## Alembic

Это инструмент миграций для SQLAlchemy. Работает просто:

- Хранит историю изменений схемы БД в виде файлов-миграций (каждый — Python-скрипт с функциями `upgrade()` и `downgrade()`)
- В самой БД есть таблица `alembic_version`, где хранится хэш текущей версии
- Когда запускаешь `alembic upgrade head` — он смотрит на текущую версию в БД, находит все непримененные миграции по
цепочке и выполняет их по порядку
- `alembic downgrade -1` — откатывает последнюю миграцию через `downgrade()`

Миграции связаны как связный список: каждый файл знает свой `revision` и `down_revision` (предыдущий).

## Хэширование

Хэш-функция берёт данные любого размера → возвращает строку фиксированной длины. Одинаковый вход всегда даёт одинаковый
выход, но восстановить вход по выходу нельзя.

**MD5** — быстрый, 128 бит. Давно считается ненадёжным, только для чексумм файлов.

**SHA-1** — 160 бит. Тоже устарел для безопасности.

**SHA-256 / SHA-512** — семейство SHA-2, стандарт сегодня. 256/512 бит, надёжны.

**bcrypt / argon2 / scrypt** — специально для паролей. Намеренно медленные (есть параметр «стоимость»),
устойчивы к брутфорсу. Argon2 — современный победитель Password Hashing Competition.

**Как хэшируют пароли:** берут пароль + случайную соль (salt) → хэшируют → хранят `хэш + соль`.
При проверке: берут введённый пароль + ту же соль → хэшируют → сравнивают. Соль нужна, чтобы одинаковые пароли
давали разные хэши и ломали rainbow tables.

## Docker Compose — детально

Docker Compose — инструмент для запуска **многоконтейнерных приложений**. Всё описывается в одном файле `docker-compose.yml`.

### Структура файла

```yaml
version: "3.9"

services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/mydb
    depends_on:
      - db
    volumes:
      - .:/app
    networks:
      - backend

  db:
    image: postgres:15
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: mydb
    volumes:
      - pg_data:/var/lib/postgresql/data
    networks:
      - backend

volumes:
  pg_data:

networks:
  backend:
```

### Ключевые секции

**`services`** — каждый сервис это отдельный контейнер. Внутри:

- `image` — готовый образ с Docker Hub
- `build` — путь к `Dockerfile`, compose соберёт образ сам
- `ports` — проброс портов `хост:контейнер`
- `environment` — переменные окружения
- `volumes` — монтирование папок или именованных томов
- `depends_on` — порядок запуска (но не ждёт готовности приложения, только старта контейнера)
- `networks` — к каким сетям подключён контейнер
- `restart: always` — политика перезапуска при падении

**`volumes`** — именованные тома. Docker сам управляет хранилищем, данные живут между перезапусками контейнера.
Без этого данные БД умрут при `docker compose down`.

**`networks`** — изолированные сети. Контейнеры в одной сети видят друг друга **по имени сервиса**
(то есть `db` — это уже hostname). По умолчанию compose создаёт одну общую сеть для всех сервисов.

### Как это работает под капотом

1. Compose читает yml → создаёт изолированную Docker-сеть для проекта
2. Поднимает контейнеры в нужном порядке (с учётом `depends_on`)
3. Каждый контейнер получает DNS-имя равное имени сервиса — поэтому `db:5432` работает как адрес
4. Именованные volumes монтируются в нужные пути внутри контейнеров

### Основные команды

```bash
docker compose up -d          # запустить в фоне
docker compose down           # остановить и удалить контейнеры
docker compose down -v        # + удалить volumes (осторожно: данные сотрутся)
docker compose build          # пересобрать образы
docker compose logs -f web    # логи конкретного сервиса
docker compose exec web bash  # зайти внутрь контейнера
docker compose ps             # статус всех сервисов
```

### `.env` файл

Compose автоматически подхватывает `.env` из той же папки:

```env
POSTGRES_PASSWORD=secret
```

```yaml
environment:
  POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
```

### `depends_on` с проверкой готовности

Стандартный `depends_on` не ждёт, пока БД реально примет соединения. Для этого используют `healthcheck`:

```yaml
depends_on:
  db:
    condition: service_healthy

db:
  image: postgres:15
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U user"]
    interval: 5s
    timeout: 5s
    retries: 5
```

Вот так compose ждёт настоящей готовности сервиса перед запуском зависимых.
