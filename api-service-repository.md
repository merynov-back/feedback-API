# Слоистая архитектура: API → Service → Repository

## 1. Зачем это нужно

Базовая идея — разделение ответственности (Separation of Concerns). Каждый слой решает одну задачу и не лезет в чужую зону ответственности. Это даёт:

- замену реализации одного слоя без переписывания остальных (например, поменять БД с Postgres на Mongo — поменяется только репозиторий);
- тестируемость — каждый слой можно тестировать изолированно, подменяя соседние слои моками;
- читаемость — новый разработчик понимает, где искать логику конкретного типа;
- контроль направления зависимостей — нижние слои не должны знать о верхних.

## 2. Три слоя и их зона ответственности

### API / Controller / Handler layer
Точка входа в систему. Отвечает за транспортный протокол (HTTP, gRPC, WebSocket).

Делает:
- парсинг запроса (path params, query, body, headers);
- валидацию формата входных данных (DTO/схемы);
- вызов нужного метода сервиса;
- маппинг результата или ошибки в HTTP-ответ (коды статусов, тело ответа);
- авторизацию/аутентификацию на уровне запроса (через middleware).

Не делает: бизнес-логику, прямые обращения к БД, транзакции.

### Service / Use Case layer
Сердце системы — бизнес-логика.

Делает:
- оркестрацию: вызывает один или несколько репозиториев, внешние сервисы, очереди;
- проверку бизнес-правил (например, «нельзя списать больше, чем на балансе»);
- управление транзакциями (начало/коммит/откат, если несколько репозиториев должны быть согласованы);
- преобразование данных между доменной моделью и тем, что нужно вызывающей стороне;
- генерацию доменных ошибок (не HTTP-ошибок — это задача API-слоя их транслировать).

Не делает: не знает про HTTP/gRPC, не формирует HTTP-коды, не пишет SQL напрямую (только через интерфейс репозитория).

### Repository / Data Access layer
Абстракция над хранилищем данных.

Делает:
- CRUD-операции и более сложные выборки;
- маппинг строк БД / документов в доменные сущности и обратно;
- изоляцию деталей конкретной БД (диалект SQL, ORM, индексы, кэш).

Не делает: бизнес-логику, валидацию бизнес-правил, ничего не знает о том, кто её вызывает.

## 3. Как это выглядит в потоке запроса

```
HTTP запрос
   │
   ▼
[Controller] — парсит запрос, валидирует DTO
   │  вызывает service.method(dto)
   ▼
[Service] — проверяет бизнес-правила
   │  вызывает repository.find(), repository.save()
   ▼
[Repository] — формирует SQL/ORM-запрос
   │
   ▼
[База данных]
   │
   ▲ результат поднимается обратно тем же путём,
   │ на каждом слое преобразуясь в нужный вид
HTTP ответ
```

Пример (псевдокод, условный TS/NestJS-стиль):

```ts
// Controller
@Post('/orders')
async createOrder(@Body() dto: CreateOrderDto) {
  const order = await this.orderService.create(dto);
  return OrderResponseMapper.toResponse(order); // 201 + JSON
}

// Service
class OrderService {
  constructor(private orderRepo: OrderRepository, private stockRepo: StockRepository) {}

  async create(dto: CreateOrderDto): Promise<Order> {
    const stock = await this.stockRepo.findByProduct(dto.productId);
    if (stock.quantity < dto.quantity) {
      throw new InsufficientStockError(); // доменная ошибка
    }
    const order = Order.create(dto);
    await this.stockRepo.decrease(dto.productId, dto.quantity);
    return this.orderRepo.save(order);
  }
}

// Repository
class OrderRepository {
  async save(order: Order): Promise<Order> {
    const row = await this.db.insert('orders', toRow(order));
    return toDomain(row);
  }
}
```

## 4. Проектирование: на чём строится связность слоёв

### Интерфейсы и инверсия зависимостей
Сервис не должен зависеть от конкретной реализации репозитория — только от интерфейса (`OrderRepository` как абстрактный контракт). Это принцип Dependency Inversion (буква D в SOLID). Конкретная реализация (`PostgresOrderRepository`, `InMemoryOrderRepository` для тестов) подставляется через DI-контейнер.

```ts
interface OrderRepository {
  save(order: Order): Promise<Order>;
  findById(id: string): Promise<Order | null>;
}
```

Это позволяет в юнит-тестах сервиса подставлять fake/mock-репозиторий без поднятия реальной БД.

### DTO vs Domain Entity vs DB Model
Часто это три разных набора объектов:
- **DTO** — то, что приходит/уходит через API (плоские структуры, валидируются библиотекой типа class-validator/zod);
- **Domain Entity** — объект с бизнес-логикой и инвариантами, живёт внутри сервисного слоя;
- **DB Model / Row** — структура, привязанная к схеме таблицы или ORM.

Маппинг между ними — отдельная (часто недооценённая) часть проектирования. Без него слои начинают "протекать" друг в друга (например, ORM-аннотации просачиваются в контроллер).

### Где границы транзакций
Транзакция — это ответственность сервисного слоя, а не репозитория, потому что именно сервис знает, какие несколько операций должны быть атомарны. Репозиторий обычно предоставляет метод для работы "в рамках" переданной транзакции/сессии.

### Куда класть валидацию
- Формальная валидация (типы, обязательность полей, формат email) — на уровне API/DTO.
- Бизнес-валидация (есть ли товар в наличии, имеет ли пользователь право) — на уровне Service.

## 5. Частые ошибки в проектировании

- **Толстый контроллер** — бизнес-логика просочилась в API-слой, сервис превращается в простую прокладку.
- **Анемичный сервис** — сервис просто дёргает репозиторий 1-в-1 без какой-либо логики; в таком случае слой сервиса вообще не нужен, можно объединить.
- **Утечка ORM-сущностей наружу** — контроллер возвращает напрямую объект из ORM, из-за чего меняется API-контракт при любой миграции схемы БД.
- **Сервис напрямую обращается к БД**, минуя репозиторий — теряется смысл абстракции.
- **Циклические зависимости между сервисами** — обычно сигнал, что границы доменов выбраны неверно (см. ниже про DDD).
- **Один репозиторий = один файл с сотней методов** — стоит выделять методы по агрегатам/use-case, а не множить "findByEverything".

## 6. Куда это расширяется в более сложных системах

- **Domain-Driven Design (DDD)**: вводится явный domain layer между Service и Repository — Aggregate, Entity, Value Object, Domain Event. Service (Application Layer) становится тонким оркестратором, а бизнес-правила переезжают внутрь доменных сущностей.
- **CQRS**: разделение Command (запись, через Service → Repository) и Query (чтение, часто напрямую через отдельный read-репозиторий/проекцию, в обход доменной модели — ради скорости).
- **Unit of Work**: паттерн, оборачивающий несколько репозиториев в одну транзакцию, чтобы Service не управлял транзакциями вручную.
- **Hexagonal / Clean Architecture**: API и Repository становятся "адаптерами" (drivers/driven), а Service/Domain — "ядром", которое ни о чём внешнем не знает. Зависимости всегда направлены внутрь, к ядру.

## 7. Краткое сравнение слоёв (таблица для быстрого повторения)

| Слой | Знает про HTTP | Знает про БД | Содержит бизнес-логику | Типичные классы |
|---|---|---|---|---|
| API/Controller | да | нет | нет | Controller, Handler, Middleware |
| Service | нет | нет (только через интерфейс) | да | UseCase, Service, Application Service |
| Repository | нет | да | нет | Repository, DAO, Mapper |

## 8. Главное, что нужно запомнить

Зависимости идут сверху вниз через интерфейсы: Controller → Service → Repository-интерфейс ← Repository-реализация. Каждый слой не должен "знать" больше, чем ему нужно для своей задачи. Чем строже соблюдается это разделение, тем легче система переживает рост и смену технологий.
